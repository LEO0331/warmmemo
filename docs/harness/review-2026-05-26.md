# WarmMemo Harness Review (2026-05-26)

This review is based on the harness-engineering principle that one giant instruction file degrades agent performance through context bloat, weak priority signals, and poor task routing.

Reference:
- [Learn Harness Engineering: 第四講. 把指令拆分到不同檔案裡](https://walkinglabs.github.io/learn-harness-engineering/zh-TW/lectures/lecture-04-why-one-giant-instruction-file-fails/)

## Current state review

### What was already good

1. The project already had split operational docs:
   - `docs/info.md`
   - `docs/progress.md`
   - `docs/flow.md`
2. The existing `claude.md` was relatively short and already acted as a partial router.
3. Architecture and stakeholder deep dives already lived outside the runtime entry surface.

### Gaps

1. There was no repo-local `AGENTS.md` router.
   - That meant project-specific routing depended on external session instructions or tool-specific habits.
2. Task-to-file loading paths were implied, not explicit.
   - Agents had to infer what to read for auth, payment, Firestore rules, or admin work.
3. Verification expectations existed, but were split across multiple places.
4. Harness guidance was mixed with product guidance instead of having a dedicated operating layer.

## Changes added in this pass

1. Added root `AGENTS.md` as a short router.
2. Added `docs/harness/` as the topic-specific harness layer.
3. Added explicit task-routing guidance.
4. Added a verification matrix so completion claims are backed by the right checks.
5. Updated existing docs to point to the harness layer instead of assuming one generic instruction file.

## Why this structure was chosen

### Chosen structure

- `AGENTS.md`
  - short router
  - hard constraints
  - quick-start verification commands
  - topic links
- `docs/harness/*.md`
  - task-specific operating guidance
- existing project docs
  - product, flow, architecture, progress

### Why not keep everything in `claude.md`

- It would make one tool-specific file the de facto knowledge base.
- The project would remain dependent on a single long prompt surface.
- Routing quality would degrade as more project history accumulates.

### Why not create many micro-files immediately

- Too many tiny files create lookup overhead and fragmentation.
- The project does not yet need per-feature harness files for every module.
- A small router + three focused harness docs is enough for the current complexity.

## Review conclusions for this repo

### Recommendation 1: keep root guidance under 200 lines

Applied:
- the new `AGENTS.md` is intentionally short and routing-focused.

### Recommendation 2: keep task-heavy guidance out of the root

Applied:
- task mapping moved into `docs/harness/task-routing.md`
- verification policy moved into `docs/harness/verification-matrix.md`

### Recommendation 3: keep historical lessons out of prompt files when tests can enforce them

Project status:
- mostly aligned already
- continue converting recurring regressions into tests instead of prose

### Recommendation 4: keep product docs and harness docs separate

Applied:
- product behavior remains in `docs/info.md`, `docs/flow.md`, `docs/progress.md`
- agent operating behavior now lives in `docs/harness/*`

## Next steps

1. If `claude.md` grows materially, trim it to a pointer file or align it directly to `AGENTS.md`.
2. If Patrol coverage grows, add a short UI-verification routing note for which flows require browser-level validation.
3. If backend/Cloud Functions become active again, add one dedicated harness doc for server-side deployment and secret-handling tasks.
